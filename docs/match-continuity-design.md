# 2D 比赛连续性与动作节奏改造方案 v0.1

状态：**阶段 A + 阶段 B（v3）已实施并验证；后台批量比赛仍用 v2。**

## 1. 结论与目标

当前的主要问题不是“圆点刷新次数不足”，而是：**一次完整动作跨度偏大，出脚被安排得偏晚，动作期间缺少持续更新的接应、逼抢和回追。**

采用两阶段路线：

1. **阶段 A：修正播放时序。** 不改变权威比赛结果，把准备、出脚、飞行、接球表达清楚，修复运动采样和播放时钟问题。
2. **阶段 B：引入连续比赛过程。** 在新规则版本中，将跑位、动作状态和结果判定分离；连续更新局面，重要事件才触发相应判定。

不是把现有 `engine.step()` 每秒调用十次，也不是仅把展示层从 10 Hz 调到 60 Hz。

### 1.1 用户可感知的目标

- 普通短传不再普遍出现“站住一两秒，然后才把球踢走”。
- 球在飞行时，接球人、逼抢人和保护队友仍在对局面作出反应。
- 短传、长传、盘带、射门、争抢有不同节奏，而不是统一填满一个大回合。
- 连续传递可以衔接，球员不会普遍在同一个回合边界一起转向、一起停下。
- 暂停、倍速、网络抖动不改变比赛结果，不造成长期队列积压或速度突变。

### 1.2 非目标

- 不声称复刻 FM 的内部比赛引擎；现有项目文档里的 FM 采样率描述，不足以证明我们的行为模拟等价。
- 不在本轮加入 3D、骨骼动画、通用刚体碰撞或复杂套路学习系统。
- 不通过随机抖动、全员不停跑动或整体倍速来伪装连续性。
- 不把联赛现实 600 秒改成 90 分钟，也不直接将逻辑时长扩大六倍。
- 不在本轮补齐历史比赛的完整 2D 录像存储。当前赛后主要是文字回放，12 帧环形缓冲不是完整录像。

## 2. 当前证据与边界

### 2.1 已检查的实现

| 文件 | 当前行为 | 影响 |
| --- | --- | --- |
| `src/game/match/engine.ts`：`openPlay()` / `moveAll()` | 一次选择动作，按完整准备/执行时长批量移动，再结算动作 | 动作中间缺少持续感知和调整 |
| `src/game/match/engine.ts`：`desiredTarget()` | 非盘带的持球人一般以当前位置为目标 | 传射前容易站定等待 |
| `src/game/match/visualization.ts`：`samplePlaybackFrame()` | 普通球路大约在片段 90% 时到达；由飞行时长倒推出脚时刻 | 短传也可能被迫等待大半个片段 |
| `src/game/match/motion.ts` | 10 Hz 运动层追逐已确定的插值目标 | 改善位移外观，不增加比赛行为 |
| `src/ui/pitch-canvas.ts`：`advanceMotion()` | 同一渲染帧需要补多个 tick 时，重复使用同一个目标样本 | 高倍速或低帧率下目标速度估计可能失真 |
| `src/ui/match-timing.ts` | 友谊赛按每步逻辑时长换算现实播放时间，并逐步限幅 | 总观看时间与步骤切分存在耦合 |

### 2.2 本次静态模拟基线

种子 `2024…2031`；每个种子通过 `createInitialGame(seed)` 建队，双方镜像阵容，非淘汰赛，逻辑时长 900 秒。它是小样本诊断，不代表全联赛分布。

| 指标 | 结果 |
| --- | ---: |
| 平均引擎步骤 / 场 | 220.1 |
| 平均逻辑秒 / 步 | 4.09 |
| 900 秒铺满 10 Hz 的理论运动 tick | 9,000 |
| 非定位球传球片段数（8 场合计） | 859 |
| 正常档传球片段平均现实播放时间 | 2.50 秒 |
| 平均出脚前现实等待 | 1.62 秒 |
| 出脚前等待比例的片段平均值 | 65.5% |
| 传球人起终点距离小于 0.01 米的片段占比 | 89.8% |

步数基线可通过 `npm run match:motion` 复现；没有安装 tsx 时，支持 TypeScript 类型擦除的 Node 也可运行 `node --experimental-strip-types scripts/motion-profile.ts`。

传球统计来自本次临时诊断：用 `planMatchReplay()` 收集完整轨迹，筛选 `motion.kind === 'pass' && !restart`，按当前 `samplePlaybackFrame()` 的 release/flight 公式和 `friendlyStepMs(seconds, 2700)` 计算。阶段 A 开始前应将该统计固化为脚本，不把临时结果冒充已有回归测试。

**没有实测此次用户环境的浏览器 FPS。** 不能排除设备负载、页面重绘、GC 或网络造成额外卡顿；行为拖沓与渲染掉帧需要分别测量。

### 2.3 对旧研究结论的修正

`docs/2d-animation-research.md` 的运动层仍有价值，但“只加运动层即可解决、不需要增加判定密度”过于绝对。

应区分三件事：

- **采样密度**：位置记录够不够密，插值是否稳定。
- **行为密度**：局面多久更新一次，能否在动作中途调整跑位。
- **结果判定次数**：完成了多少次传球、射门、对抗。

提高行为密度，不等于同比增加传射判定次数；也不能把现有每步进球率线性外推，作为新架构必然失衡的证明。

## 3. 时间与频率契约

### 3.1 保留三种时间

| 时间 | 用途 | 首版设定 |
| --- | --- | --- |
| 逻辑时间 | 移动、球路、动作阶段、事件时刻 | 全场 900 秒，单位为逻辑秒 |
| 比赛显示时间 | 比分栏、文字直播、换人分钟 | 映射到 90 分钟 |
| 现实时间 | 播放、服务器联赛进度 | 联赛 600 秒；友谊赛可暂停、倍速 |

不把 90 分钟显示钟当成物理积分时间。定位球准备也消耗逻辑时间；中场展示是否额外占用现实时间必须独立定义，不能暗中改变联赛截止时间。

### 3.2 阶段 B 的初始频率

以下是待基准测试的设计参数，不是对 FM 内部频率的声明。

| 层 | 初始频率 / 触发 | 职责 |
| --- | --- | --- |
| 权威运动积分 | 固定 0.1 逻辑秒 | 位置、速度、转向、球的运动 |
| 无球意图更新 | 通常 0.2–0.5 逻辑秒一次，重要事件可唤醒 | 接应、压迫、盯防、保护空间 |
| 持球动作决策 | 接球处理完成、动作取消、球权变化等事件 | 选择传球、盘带、射门 |
| 对抗/结果判定 | 出脚、进入拦截窗口、到达落点等事件 | 每个明确机会只判定一次 |
| 轨迹记录 | 默认 10 Hz，额外记录重要事件边界 | 供播放、调试与导出消费 |
| 网络发送 | 初始每现实秒 4 次，批量发送 | 不要求一个 tick 一个 HTTP/SSE 消息 |
| 浏览器绘制 | RAF，参考 60 Hz 屏幕 | 对已确认轨迹插值 |

球路碰撞/拦截用相邻采样之间的连续线段或解析交点检查，不能仅测试每 0.1 秒的离散位置，避免高速球穿过防守人。

## 4. 阶段 A：先修播放时序，不改赛果

### 4.1 引入版本化的动作时间线

在 `MatchPlaybackFrame` 上新增可选 `timeline`，保留旧帧读取能力。阶段 A 中它是**视觉编排元数据**，不是新的权威事件时间。

```ts
type PlaybackTimeline = {
  version: 1
  segments: Array<{
    kind: 'prepare' | 'carry' | 'flight' | 'receive' | 'settle'
    start: number // 相对 frame.from.clock 的逻辑秒
    end: number
    actorId?: string
    targetId?: string
    from?: PitchPoint
    to?: PitchPoint
  }>
}
```

约束：

- 时间单调，所有片段都在当前帧区间内；零时长事件单独处理，不除以零。
- 普通传球：准备 → 飞行 → 接球/后续移动；不再固定在 90% 时落地。
- 传中接头球、扑救反弹等复合动作使用多段球路，不依赖一个 `via` 加固定 65% 分割表达所有情况。
- 默认参考动作属性和球路距离编排；不读取或推进权威随机数，不给阶段 A 引入新的比赛结果。
- 短传准备期先以 **0.25–0.7 逻辑秒**做试验；该范围不是所有传球的硬上限，停球困难、定位球不适用。
- 飞行时间由距离、动作类型和速度模型决定；新代码只保留一套被实际调用的球路计算，避免 `motion.ts`、`visualization.ts`、`match-timing.ts` 各有一套不同公式。

### 4.2 提前出球不能变成提前瞬移

更早到达时，接球人可能尚未抵达旧终点。必须联合求解出脚点、接应路径和落点，而不是单纯把 `arrival = 0.9` 改成 `0.4`。

首版策略：

1. 从已有端点和相邻轨迹构造有限的视觉路径。
2. 在候选接球时刻检查球员可达范围和球的飞行时间。
3. 能满足约束时，选择较早的合理接球时刻；接球后球随已显示的接球人移动。
4. 无法满足时保留更长的准备/飞行，记录 `timingFallback`，不瞬移接球人，也不把球强行吸到脚下。
5. 同一飞行段开始后锁定轨迹；不能每帧把落点向滞后的圆点拉动，形成追踪球。

**阶段 A 保留整步时长和事件结果，因此不能保证增加单位时间内的传球次数。** 提前出球后，剩余时间可能转移到接球后；不能简单改成“下一个人拿球等”。已有轨迹不足以表达后续处理时，保守回退并暴露指标，交给阶段 B 解决。

### 4.3 修正运动采样与时间推进

- 补多个 tick 时，对每一个固定逻辑时刻采样各自目标，而不是重复喂当前 RAF 的同一坐标。
- 播放时钟暴露本次真正消费的逻辑区间；跨动作片段时按实际区间推进，不用最后一个片段的 rate 估算全部时间。
- `MatchPlayback.sample()` 当前会修改播放游标。新增“推进时钟”和“按绝对逻辑时刻纯采样”两个接口，避免为了补 tick 重复消费队列。
- 暂停与恢复重设现实时间基准，不能补算暂停时长。
- 超大断线间隔显式切入新快照，记录 discontinuity；不靠全队追赶或无限加速补齐。
- 首次载入、开球重置、换人、断线分别统计，不能把正常比赛漂移都归类为合法瞬移。

### 4.4 阶段 A 的发布边界

- 权威比分、事件、属性、体能、统计、随机数状态全部与原规则一致；比较时排除新增视觉字段。
- 不改 `MATCH_RULES_VERSION`，只版本化视觉数据。
- 不修改现有文字事件时间来配合画面；因此本阶段不能宣称已经实现精确的声画/文字同步。
- 提供旧/新播放策略开关，用同一批已确认动作进行 A/B 对照。
- 如果只把“传球前等”变成“接球后等”，不能以出脚指标下降宣告成功。

## 5. 阶段 B：连续运动 + 动作状态机 + 事件判定

### 5.1 模块边界

```text
权威输入：阵容 / 战术 / 指令 / 固定随机数状态
                    ↓
行为层：选择意图、动作、反应时间
                    ↓
固定步长仿真：球员运动 + 动作阶段 + 球路
                    ↓
事件裁决：出脚、拦截、接球、射门结果、死球
                    ↓
权威状态 / 统计 / 日志 / 已确认轨迹
                    ↓
浏览器播放：缓存、时间插值、绘制
```

阶段 B 后，物理限制进入权威仿真。客户端不再运行一套独立追逐器把权威位置“追歪”，再修正球路去追客户端圆点。

`motion.ts` 中可复用的速度、加速度、转向计算抽成纯函数；取消正常比赛中的 catch-up 超速和距离阈值瞬移。显式重置仍可用于开球、换人和断线切入。

### 5.2 球员意图与动作分开

无球意图至少区分：保持阵型、提供接应、前插、逼抢、盯防、回追、保护空间。

- 每个意图有目标点、关注对象、下一次评估时刻和最短保持时间。
- 从同一 tick 起始快照计算全队目标，再统一积分，避免数组处理顺序使一方获得先移动优势。
- 球权变化、球路进入本区域等事件可提前唤醒相关球员。
- 加入意图保持和切换阈值，避免球轻微移动就全员左右抖动。
- 意图更新时刻按稳定 ID 错峰；不引入不可复现的现实计时器。
- 允许合理站住，不用“所有球员一直动”作为验收目标。

### 5.3 动作状态机

示意结构，完整字段以实施时序列化需求为准：

```ts
type ActionState = {
  id: number
  kind: 'pass' | 'dribble' | 'shot' | 'clear' | 'restart'
  actorId: string
  targetId?: string
  phase: 'prepare' | 'execute' | 'recover'
  startedAt: number
  nextBoundaryAt: number
  plannedTarget: PitchPoint
}
```

接球/球的状态另行记录，不要求一名球员的恢复结束后全队才可以行动。

典型传球流程：

1. 持球人选择传球，进入准备；队友和对手继续移动。
2. 准备阶段允许有限调整朝向、护球和小幅带球；不能自由改变已锁定动作而又不付出时间。
3. 出脚前再次检查最低合法条件；若发生抢断、犯规或目标失效，显式取消/改选。
4. 出脚时冻结起点、初速度、目标和误差，`ownerId = null`；越位快照取此时刻。
5. 飞行期间，双方继续接应或压迫；只在有效拦截窗口触发一次对应对抗。
6. 球进入可控制范围后进入接球处理；处理完成产生球权确认，再允许下一次持球决策。
7. 一脚传球需要提前准备与满足接球条件，不通过“零耗时反复 step”实现。

射门的机会质量与压力取出脚时快照；飞行中封堵、门将处理与出脚前压力分开，不能让后到的防守人倒改射门难度。

### 5.4 球的状态

至少区分：`controlled`、`flight`、`loose`、`dead`。

- controlled：有合法持球人，位置跟随权威球员运动。
- flight：无持球人，采用固定球路和剩余飞行时间；拦截/折射可终止旧球路并创建新球路。
- loose：双方争夺可达落点，不直接分配给最近者。
- dead：定位球准备与发球阶段，不能继续判开放比赛抢断。

不能同时保留“每 tick 物理拦截”和“动作结束时旧概率再抽一次断球”两套结算。同类结果必须迁移到一个裁决入口。

### 5.5 tick 内的事件顺序

基础步长 0.1 秒，但动作边界可以位于两个 tick 之间：

1. 读取指令与到期意图，基于同一快照确定输入。
2. 查找当前区间最早的动作边界、球路交点、半场/终场边界。
3. 积分到该边界，裁决事件，更新状态，再积分剩余区间。
4. 同时事件用明确优先级和稳定 ID 排序；例如犯规中止后的旧出脚事件必须失效。
5. 每个事件有稳定 ID、已处理标记；取消动作后关联事件不能再执行。
6. 限制单 tick 内事件链深度；零时间循环视为引擎错误并输出诊断，不静默产生无限传球。

这样既不要求每秒重做十次完整传射判定，也不会把所有接球、出脚强行量化到同一个 0.1 秒边界。

## 6. 规则、概率与确定性

### 6.1 分清“按时间”和“按机会”计费

| 项目 | 新口径 |
| --- | --- |
| 跑动体能、恢复 | 距离、速度、加速度与实际耗时；不是每 tick 固定扣一笔 |
| 出场时间、控球统计 | 按经过的逻辑时间累加，转换为显示分钟 |
| 射门转化、一次传球误差 | 每个独立动作/事件抽样一次 |
| 抢断、封堵 | 有效对抗窗口内判定，去重并设退出/再进入规则 |
| 犯规、受伤 | 明确按对抗或按暴露时间，不能无条件每 tick 抽一次 |
| 技能触发统计 | 对应动作或对抗机会计数，不随采样率增长 |

若某风险确实按时间定义，用风险率转换 `p(dt) = 1 - exp(-lambda * dt)`；不能把所有原有动作概率简单除以 40。

### 6.2 确定性与后台一致性

- 同规则版本、同初始状态、同带时间戳的指令序列，逐 tick、批量推进、暂停后恢复应得到一致结果。
- 固定积分步和稳定事件顺序；记录 tick index 与不足整步的余量，避免按调用批次改变积分切分。
- 视觉采样和网络发包不消费随机数。
- 随机抽样绑定明确事件，保存所有 RNG 状态及待执行动作；禁止条件重试重复抽样直到成功。
- 基础 tick 不复制完整日志和整份 `MatchState`；只为需要同时读取的运动状态建立轻量快照。
- AI 后台比赛可关闭轨迹记录，但使用相同仿真规则，不能用另一套快算逻辑造成有无观众赛果不同。

### 6.3 版本升级必须显式路由

当前恢复逻辑使用 `state.rulesVersion !== MATCH_RULES_VERSION` 判断 legacy。**不能只把常量从 2 改到 3，否则 v2 会被误送到更老的规则分支。**

设计要求：

- 将恢复改成明确的规则分派：无版本/历史版本、v2、v3 分别处理；未知未来版本拒绝加载并明确报错。
- v2 进行中的比赛继续由冻结的 v2 引擎完成，不在半场切换规则。
- v3 仅用于升级后新建的比赛；赛季中是否启用由配置决定，默认赛季边界统一切换。
- v3 保存动作、球路、速度、朝向、意图、事件序号、RNG、时间余量及指令生效边界。
- 序列化 schema 版本与比赛规则版本分离；仅增加显示字段不应升级比赛规则。
- 回滚配置只影响新比赛；已有 v3 活动比赛必须保留 v3 执行能力，不能用旧二进制强行恢复。

## 7. 实时联赛、友谊赛与 Agent 接口

### 7.1 权威时钟与播放时钟分离

- 联赛继续按服务器现实进度映射到逻辑时刻，客户端不决定比赛何时发生。
- 阶段 B 的 `advanceTo(targetClock)` 只提交目标时刻以内的权威状态和事件。
- 不能直接沿用当前实时推进中“试跑下一整步，只检查新增日志时间”的做法；新协议要求状态时刻、轨迹终点、事件时间都不超过已确认边界。
- 服务器内部即使为计算而推演未来，也不能将未来轨迹、比分、动作结果或完整 RNG 状态作为公共播放数据发给客户端。

### 7.2 有界播放缓冲

- 初始目标缓冲 **0.6–1.0 现实秒**，只播放已有前后两个采样点的已确认区间。
- 每批包含 `matchId`、规则/协议版本、单调序号、`confirmedClock`、轨迹片段及对应事件。
- 正常网络下通过小幅时钟校正（候选 ±5%）恢复缓冲；饥饿时保持最后确认姿态，不预测传球成功或进球。
- 不把网络等待累加到每个动作中，避免越播越落后。
- 正常比赛画面的比分、文字与球场使用同一播放游标；权威结果可已结算，但前端先播完最后动作再进入赛后页。
- 长断线允许显式切入最新快照，并提示“已同步到最新进度”；不强制补播所有丢失画面。
- 纯文字/管理接口可以返回权威当前状态，但不得将其未来比分混入落后的球场播放 HUD。

### 7.3 友谊赛倍速

- 阶段 B 用全局逻辑播放速率替代“每个动作各自限幅”；先采用慢 1×、正常约 1.5×、快约 3×。
- 一场观看长度由总逻辑时长和速率决定，不随动作数改变。
- 变速时保留当前位置和逻辑游标，不重启动画、不重抽动作。
- 暂停冻结本地友谊赛推进；联赛只能暂停观看，服务器继续比赛，恢复时按缓存或切入策略处理。
- 友谊赛若保留预演，教练调整只废弃生效边界之后的预演；已确认轨迹不可改写。

### 7.4 `step()` 与 `advance_match`

- v2 原接口保持原语义。
- v3 新增内部 `advanceTicks(n)`、`advanceTo(clock)`；不能把 MCP 的 `steps=1` 悄悄解释为 0.1 秒。
- v3 兼容包装 `step()` 推进至下一个主要动作完成/死球边界，包含必要的小 tick；返回 `fromClock`、`toClock` 和实际推进量。
- 若达到最大推进预算仍无主要事件，返回明确的部分进度；不得无限等待。
- MCP 文档明确 v3 的语义，可新增按逻辑秒推进参数；与 steps 互斥，联赛仍拒绝手动推进。
- 原有基于 `state.step % N` 的解说、保存、助攻窗口等逐项审查，分别迁移到时间、动作 ID 或事件 ID，不继承错误频率。

## 8. 轨迹存储与模块落点

### 8.1 数据策略

阶段 A 保留现有 12 个动作帧缓冲；阶段 B 不将完整高频轨迹内嵌到每次存档或全量 SSE 状态中。

- 活动比赛保存恢复所需权威状态；播放器轨迹独立缓冲。
- 初始保留最近 **30 现实秒**的轨迹，按逻辑时间窗口淘汰，不再按 12 个动作计数。
- 正常档约 45 逻辑秒 × 10 Hz × 14 人 = 6,300 个人位置样本；字段与 JSON 包装仍需实测。
- 全场 9,000 帧 × 15 个对象 × 2 个 float32 坐标，仅裸 XY 就约 **1.08 MB**，尚不含时间、速度、球高、事件和索引；JSON 体积会显著更大。
- 只向订阅该场比赛的客户端发送轨迹增量，不随普通游戏状态全量广播。
- 完整录像以后以分块文件/对象存储、版本化元数据实现；历史文字记录不能无条件重建精确 2D 录像。

## 9. 验收与观测

所有新增数字均为**首轮验收候选值**，未通过实测前不能标为已经达成。

### 9.1 指标定义

- `preKickWait`：动作开始至实际出脚；同时报告逻辑秒和正常档现实秒。
- `postReceiveWait`：接球处理完成至下一动作开始；与前置等待合并分析，防止转移等待。
- `idleWithBall`：非死球状态下，持球人速度低于 0.2 m/s 且没有处理动作的累计时间。
- `targetReevaluationGap`：无球目标两次有效评估的间隔。
- `unexpectedSnap`：排除显式重置后，位移超出速度/加速度许可范围的次数。
- `ballControlError`：声明 controlled 时球与持球人脚下偏移的误差；不将飞行帧计算在内。
- `bufferDepth` / `underrunMs`：已确认缓存深度与播放饥饿时间。
- `frameIntervalP95` / long tasks / GC：浏览器渲染性能，与动作节奏分开报告。

### 9.2 阶段 A 验收

1. 100 个固定种子，对比开启/关闭新视觉层：权威状态、日志、统计和 RNG 完全一致。
2. 单元场景：10–20 米、低压、普通短传，在可达性允许的情况下，正常档出脚等待 P50 ≤ 0.5 秒、P90 ≤ 0.9 秒；同步报告回退率，不能只筛成功样本。
3. 比较完整传球链的前后等待总量和连续运动，禁止仅靠把等待移到接球后通过验收。
4. 30/60/120 Hz RAF 输入、变速、跨片段、暂停恢复下，同一逻辑时刻的运动状态保持一致（数值误差建议 ≤ 0.01 米）。
5. 同一段动作由网页和 tracking 导出采样，应得到一致的阶段边界和球路。
6. 主观 A/B：至少覆盖低压短传、受压出球、长传、反击、传中射门和定位球六类片段；原速对比，不用整体加速掩盖问题。

### 9.3 阶段 B 验收

- 正常开放比赛中无意外瞬移；受控球贴脚误差在声明的视觉脚下偏移之外 ≤ 0.3 米。
- 飞行中球权为空；接球、拦截、进球只结算一次；取消动作不产生幽灵事件。
- 100 个固定种子、多个中间存档点：连续推进、批量推进、恢复推进、开关轨迹记录结果一致。
- 无球意图在设定的 0.2–0.5 秒调度内执行，事件唤醒可提前；不存在全队依赖一个大回合更新的路径。
- 终场/半场边界截断正确，统计时间不多计；终场前出脚但尚未抵达的球按明确规则处理，不靠继续积分越过终场偷算结果。
- 单 tick CPU、整场 CPU、内存、网络流量有基准报告。先以同机 v2 整场耗时的 **5 倍以内**为优化目标；这是预算，不是当前性能保证。
- 基础 v3 性能验收不通过时先优化数据结构、采样和批处理，不让后台改用另一套结果算法。

### 9.4 浏览器与网络场景

- 60 Hz 参考设备连续播放 60 秒，前台帧间隔 P95 目标 ≤ 25 ms；记录设备、浏览器、球员名开关和画布分辨率。
- 100/300 ms 网络延迟、合批推送、重复包、断线重连、后台恢复、乱序批次全部测试。
- 正常网络下缓冲不随比赛时长增长；长断线只能显式切入，不能出现几分钟积压。
- 暂停后运动 tick 不增长；恢复不能补上暂停期间全部运动。
- 教练指令、换人、红牌、进球重开球、中场、点球大战、最后一脚射门分别覆盖。

### 9.5 平衡回归

阶段 A 要求不改变结果；阶段 B 不要求与 v2 同种子同比分，但必须进行同输入的配对批量比较。

- 冻结 v2 基线；弱弱、强强、强弱及不同节奏战术分别至少 200 场，配合更大种子集复核。
- 统计传球数/成功率、推进与回传、射门/xG/进球、控球、跑动、体能、伤病、犯规、牌和实力差表现。
- 若主要均值相对基线变化超过 15%，进入人工审查，不自动判定失败；同时检查置信区间和变化原因。
- 观察每脚射门质量、每次对抗风险及实际动作数，避免仅按最终比分调一个全局补偿系数。
- 明确区分“有更多合理短传”与“所有机会乘倍”；不设固定传球数作为引擎硬目标。

## 11. 风险与决策

| 风险 | 应对 |
| --- | --- |
| 提前出脚只是把空等移到接球后 | 合并统计前后等待；明确 A 阶段上限，不用虚构动作填时间 |
| 提前落点超出接球人可达范围 | 联合时间/轨迹求解；回退并记录，不瞬移 |
| 新旧物理同时存在导致球追人、人追影子 | v3 权威物理统一，客户端只插值 |
| 高频判定使犯规、伤病、技能次数膨胀 | 按时间/距离/独立机会计费，事件去重 |
| 每 tick 克隆整个引擎导致 CPU/GC 爆炸 | 增量状态、轻量双缓冲、后台关闭轨迹记录 |
| 规则升级将 v2 错判成 legacy | 显式规则工厂和中途存档回归 |
| 600 秒联赛与缓冲冲突 | 权威准时结束，前端允许有界延后；断线显式切入 |
| 新动作更快造成整场事件量失衡 | 阶段 B 独立规则与批量校准，不硬追固定事件总数 |

**最终决策：先修“出球晚、采样不一致”，随后把“跑位随局面持续变化”放进权威引擎。增加的是有效行为更新，不是机械增加传射抽签次数。**
