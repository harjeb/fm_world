# S3 十二码之夜 · 3D 技术选型

范围：[活动玩法稿](season-events-design.md) 中的点球小游戏。只让活动场景使用 3D，不替换联赛比赛引擎和回放。首个无奖励训练场已接入「挑战 → 进入 3D 点球训练场」，使用 Three.js 0.187。运行 `npm ci && npm run dev` 后打开游戏；离线和联机均可练习，不写进度或修改资产。手机真机手感与性能仍待验收。

| 层 | 选择 | 在这一罚里负责什么 |
|---|---|---|
| 3D 渲染 | Three.js（WebGLRenderer / WebGL 2），沿用 TypeScript + Vite | 球、球门、主罚手、门将和场地都用真实 3D 坐标。主罚与守门切换机位，不镜像玩家的输入。仅进入活动时动态加载。 |
| 输入与界面 | DOM/CSS + Pointer Events | 力量竖条、可拖瞄准框、圆形方向盘。用指针捕获保持拖动；单独处理取消和页面失焦，避免误起扑。瞄准点用相机射线投到门线平面，扑救角度则以门将屏幕为准。 |
| 球路与判定 | 无渲染依赖的 TypeScript 模块 | 用初速度、重力、侧弯决定球路，用球员属性和起扑时间决定手套可达范围。原型按时间解析采样球路，直接求球到达门将平面、球门平面的时刻并依序判定，不用渲染帧触发碰撞。低帧率不改变相同输入的结果。首版不加通用刚体引擎。 |
| 美术与动画 | 本地原创 GLB、关节驱动、动态球衣纹理 | `node scripts/build-penalty-art.mjs` 重新生成球员、手套、球皮和草叶贴图；用俱乐部主色、生成队徽和球员姓名/号码覆盖球衣。局部网面位移在过线结算后单独播放，不影响结果。 |
| 验证 | Vitest + 浏览器真机试玩 | 测相同种子与输入能复现、门线/横梁边界、方向未反转、不同帧率下结果一致；触屏手感和球路提示必须真机验。 |

**为什么选 Three.js**：现有客户端已经是 TS/Vite，活动只有球门前的固定场景和两套机位。Three.js 可以作为一个按需加载的渲染库接入，而不必为了一个活动引入 Unity WebGL 的独立运行时，也不需把现有界面迁到 React。暂不选 Babylon.js 并非它做不到，而是首版不需要它更完整的游戏框架。

## 场景范围与 HUD

只建一端禁区和球门后四排小看台，不建另一座球门、其他看台或完整体育场。禁区内保留草皮磨损、修剪条纹和法线纹理。装备特写可从不同角度看队服、守门员和足球。

HUD 借鉴 [eFootball 的不同力度区间](https://www.konami.com/efootball/en/page/2022/season1_patch-notes_v1-0-0) 和 [osu! 的 approach circle](https://osu.ppy.sh/wiki/en/Gameplay/Hit_object/Hit_circle) 两种反馈原则，不使用其素材。竖条给出百分比、属性决定的窗口及锁定反馈；门框上的准星是屏幕空间 SVG，不是场景几何体，呼吸和锁定动画不参与计时。减少动态效果设置关闭装饰动画，保留必要的实时力量读数。

## 验证入口

- `npm test -- tests/penalty-practice.test.ts tests/penalty-net.test.ts tests/challenge-ui.test.ts`：力量带、球路、门框、扑救时机和属性。
- `npm run smoke:penalty`：需要 Chromium，可通过 `FM_CHROME` 指定路径。以手机视口从离线挑战页进入，练习射门、触控扑救、退出与重新进入，最后模拟缺少 WebGL 2。软件渲染冒烟不代表真机帧率。

## 初始原型验收目标（历史计划）

1. 先做无奖励训练场：同一座球门，主罚视角能瞄准、锁定力度、看到落点；守门视角能从圆盘一推起扑。两端共用同一套球路/扑救判定，先不做九关和正式模型。
2. 用同一脚贴柱球对比不同起扑时刻、不同反应属性；用相同瞄准点对比绿区、过力、欠力。回放显示实际球路与手套位置，不能用随机播放的进球动画代替结果。
3. 桌面和触屏实测，手机以稳定 30 fps 为原型目标；限制像素比，先用简化阴影。退出时停止动画循环、释放 GPU 资源。不支持 WebGL 2 或初始化失败时提示并允许返回，不开启正式挑战、不扣次数。
4. 手感验证后再接九关、每日四次、首通奖励。联机正式关卡由服务端掌管开局次数与奖励，服务端可用同一 TS 判定模块重算，不直接采信客户端上报的进球或通关结果。
