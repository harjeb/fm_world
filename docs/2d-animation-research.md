# 2D 动画：要不要换引擎？还是多给几个判定回合？

结论先说：**不换比赛引擎，也不把判定回合翻倍；在现有动画层下面加一层 10 Hz 的连续运动层。**
这一层只消费已经判好的动作，不改比分、随机数、体能和统计。

本文对应两件事：

1. 研究了 `D:/fm24re/FM24_2D动画复现_技术文档.md`（下称「FM24 文档」）里反推出来的 FM24 结构；
2. 在 `src/game/match/motion.ts` 里实现了对应的运动层，并给出可复现的对比数据。

---

## 1. FM24 文档告诉了我们什么

| 主题 | 文档结论 | 对本项目的意义 |
|---|---|---|
| 采样率 | 位置 **10 Hz** tick，渲染 60 fps 插值 | 画面清晰度来自 **采样密度**，不是判定密度 |
| 一场规模 | 约 5.4 万 tick / 150 万条位置记录 | 我们不需要存这么多，可以在渲染时生成 |
| 球的轨迹 | `MATCH_BALL::get_coords(t)` 是 **解析函数**，踢出瞬间算完整条曲线，还会提前解出出界/打柱时刻 | 球不该逐帧积分，应该按“出脚—飞行—落地”三段解析 |
| 球员移动 | 预铺路径 + 可插入延迟；41 个动作各有锁定时间（`_do` / `_receive`） | 动作之间要有“收不住脚”的过程，不能瞬移 |
| 物理参数 | 速度档位 0.45–12.27 m/s、加速度 0.25–8.94、减速 1.5–4.47、转向 **192/104/53 °/s**（走/慢跑/全速） | 这些数值可以直接拿来约束圆点 |
| 决策层 | **候选登记 + 统一裁决**，权重表不在数据包里（编译进 exe） | 抄不到判定权重；我们自己的判定层已经够用 |
| 射门 | xG 是 logistic 模型（可见球门比例、距离、遮挡、角度） | 我们的 `shotModel` 已经是同类结构，不需要替换 |
| 统计 | QME 是**赛后数据生成器**，不是过程模拟 | 不适用于我们的比赛过程 |
| 2D 渲染 | 球员点 = 阴影 + halo + 球衣 + 背号 + 高亮 4–6 层贴片；线宽按 2D 系数放大 | 我们已经用 Canvas 画了同等层次 |

一句话：**FM 的“顺滑”来自 10 Hz 的位置流 + 物理约束，不是来自每 0.1 秒重新判一次传球。**

## 2. 三条路线

| 路线 | 做什么 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| A. 重写一个 tick 级比赛引擎 | 照 FM 的 10 Hz 循环重写站位/决策/运动 | 数周；决策权重只能自写 | 比分、平衡、存档全部要重做 | ❌ |
| B. 给现有判定加回合 | 把 226 步/场提到 ~9000 步/场 | 引擎 40× CPU；所有概率要重新标定 | 进球率、体能、伤病、牌全部失真 | ❌ |
| C. 在现有动画下加运动层 | 判定不变，10 Hz 铺跑动 + 解析球路 | 已实现，约 300 行 | 只影响画面 | ✅ |

### 2.1 为什么“加回合”是错的杠杆

`npm run match:motion`（8 个种子）实测：

| 指标 | 数值 |
|---|---:|
| 每场判定步数 | **226.3** |
| 每步占用的播放时间 | **3.98 秒** |
| 10 Hz 铺满 900 秒逻辑时间需要的 tick | **9,000** |
| tick / 判定 | **39.8×** |
| 引擎耗时 | **33.5 ms/场**（0.148 ms/步） |
| 每步进球率 | 0.0215（约 4.9 球/场） |
| 判定提到 10 Hz 后的进球（不改概率） | **约 194 球/场** |
| 判定提到 10 Hz 后的引擎耗时 | **约 1.3 秒/场**（只是 CPU 还能接受，平衡已经崩了） |

也就是说：把判定做到 10 Hz，**球会变成 194:194**，射门、犯规、体能、伤病同比例膨胀。
要让它回到 4–5 球，得把每个动作的收益、体能消耗、受伤概率全部除以 40，等于重做整个平衡层。
而这 40 倍的算力换来的只是“圆点更密”，用运动层可以零判定成本拿到。

### 2.2 现有画法到底差在哪

旧的回放层在两个判定点之间做**单调三次插值**：曲线很顺，但没有物理上限。
实测：**2% 的位移段超过了该球员本场的最高速度，最夸张的一段是 2.61 倍**。
观众看到的就是“接球队员一步滑到落点”，以及所有人同时到点、同时停下的节奏。

## 3. 实现了什么

### 3.1 运动层（`src/game/match/motion.ts`）

- `motionProfileOf()`：把球员属性换成本场的运动上限
  - 最高速 `5.4 + 3.2 × 速度属性`，再乘体能系数（体能 <75% 开始掉速，最低 0.62×）
  - 加速度 `0.25 + 8.69 × 加速属性`，减速 `1.5 + 2.97 × 加速属性`
  - 转向速率以敏捷缩放，按当前速度落到 FM 的 192 / 104 / 53 °/s 三档
- `MotionAgent`：固定 0.1 秒一步，朝目标加速、限速、限转向、到点收油；不会瞬移，也不会绕圈
- `MotionField`：全队 10 Hz 推进，渲染时在最近两个 tick 之间插值
- 断线补帧/换人时，位置漂移超过 18 米就地对齐，不画横穿球场

### 3.2 球（同一文件）

`planBallFlight()` / `sampleBallFlight()`：按 FM 的踢球速度档位（短传 9、中距离 17、传中 21、射门 25–33 m/s）
算飞行时间，长传用抛物线给出离地高度，起终点与引擎落点严格一致。

### 3.3 接入位置

`src/ui/pitch-canvas.ts`：`drawPitch()` 和 RAF 循环每帧把**已判好的目标位置**交给运动层，
`advanceMotion()` 推动 tick，再把插值后的位置画出来。战术轨迹视图、暂停、终场播放、教练调整都不受影响。

### 3.4 跟跑误差

运动层不是让圆点“自由散步”，它要贴着引擎给的位置。整场（230 个动作、7,445 个 tick）实测：

| 分位 | 画面位置与引擎位置的差 |
|---|---:|
| 中位数 | **0.35 米** |
| 90% | **2.38 米** |
| 99% | **9.17 米** |
| 最大 | **9.99 米**（= 对齐阈值） |

超过 10 米就说明引擎把这个人直接挪走了（定位球站位、换人、开球），这时**只对齐这一个人**，
不让全队一起跳；整场约 0.3% 的“球员×tick”会走这条路径。进球后的下一步会标记成 `restart`，
画面直接切到中圈，不会画成一次 30 米的回追。

### 3.5 不落盘

9,000 个 tick × 14 人 ≈ 5 MB/场，**不会写进存档**。
存档里仍然只有每步的位置脚本（最多 12 帧的环形缓冲），tick 流在渲染时按属性确定性重建；
暂停、断线、重开页面都能从同一帧得到同一条轨迹。

## 4. 验证

```bash
npx vitest run tests/match-motion-engine.test.ts   # 10 条：物理上限、确定性、结果不变
npm run match:motion                               # 上面的成本对比
npm run smoke:animation                            # 浏览器实跑：10 Hz tick / 暂停 / 终场 / 比分不变
```

测试覆盖的关键不变量：

- 速度 ≤ 属性上限、单 tick 加速 ≤ 加速度上限、转向角 ≤ 当前速度的转向速率；
- 同一份输入两次推进结果完全一致；
- 喂完整场帧序列后，帧、比分、事件、随机数**一字未改**；
- 整场所有采样点都在球场内；
- 浏览器里正常播放 5 秒约 45–49 个 tick，暂停后 tick 不再增长；
- 同一时刻采样 1 秒，最快的人约 4.5 m/s，同时至少有 1 个人基本站住（不是全队一起动）。

## 5. 如果以后还要更进一步

FM24 文档里还有两块没吃进来，按性价比排序：

1. **动作锁定时间**（§4.4 的 41 个动作，500–3000 ms）。
   现在运动层已经在跑，但“传球后 0.5 秒不能立刻转身”还没做。加上它，传切会更有重量感。
   成本：在 `MatchPlaybackFrame` 里带上动作类型，运动层读锁定表；不影响判定。
2. **提前解算球的出界/打柱**。现在的球路已经解析，但边界处理还是靠引擎给的落点。
   成本中等，收益主要是边线球和门柱的镜头感。

不建议做的：

- 把判定换成 FM 的 tick 循环（路线 A）：决策权重不在数据包里，抄不到；而且会推翻现有平衡。
- 复刻 `.pkm` / `.rec` 解码：与玩法无关，只是拿真实数据校准，投入产出比低。
- 把 QME 统计模型接进比赛：它只生成赛后数据，不生成过程。
