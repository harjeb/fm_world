# 游戏设计评审与改进建议

## 1. 评审范围与结论

本评审基于当前仓库的 README、游戏规则和关键实现，重点检查玩法循环、成长、经济、联赛节奏与多人一致性。未进行长期真人试玩、并发压测或完整战术对抗实验。

**总体判断：目前是内容较完整的单机养成与云存档原型，具备扩展为多人足球经理游戏的潜力，但尚不能视为公平、统一结算的多人竞技产品。**

下一阶段应优先修复经济漏洞、明确多人世界模型、减少重复操作并增加决策取舍，而不是继续增加球员、技能和系统数量。

本文区分两类结论：

- **已确认的实现问题**：能从代码直接确认，例如市场套利路径、球队分配回退逻辑、客户端快照上传。
- **待验证的设计风险**：需要模拟或玩家测试验证，例如成长同质化速度、训练疲劳感、战术是否存在唯一最优解。

## 2. 当前值得保留的设计

### 2.1 核心循环完整

培养 → 排阵 → 比赛 → 复盘 → 调整，已经形成完整闭环。培养成果能够用于比赛，比赛反馈又能引导后续培养。

### 2.2 七人制有辨识度

较小阵容降低理解成本，也更容易突出单个球员、职责和换人的价值。后续应继续围绕七人制设计，而不是单纯缩小十一人制的数值。

### 2.3 复盘具备解释能力

机会质量、技能触发、关键事件概率和失败原因，比单纯显示比分更有价值。它们能帮助玩家理解“为什么输了”和“下次应该改什么”。

### 2.4 Agent 接入是差异化方向

Agent 可以承担日常训练、阵容维护和经营建议。建议坚持“人负责关键决策、Agent 减少重复劳动”，避免演变成“谁自动点击得更多谁赢”。

## 3. 问题与改进建议

### 3.1 多人世界并非统一的竞技世界

**优先级：P0｜性质：实现现状与产品定位问题**

代码依据：

- `src/game/world.ts`：`createWorldGameFromWorld()` 使用 `structuredClone(base)` 创建账号自己的世界。
- `server/app.ts`：`advanceAccount()` 推进各自的 `account.game`；共享世界另外推进。
- 注册逻辑优先寻找无主二级球队，用完后回退到 `choices[db.accounts.length % choices.length]`，随后写入球队归属。

当前共享了世界初始数据、时间与归属信息，但玩家比赛并非全部落在同一个权威赛程、积分榜上。不能把它直接宣传为“所有玩家经营的球队在同一联赛中交锋”。

初始二级联赛南北区共 40 支球队；没有可用无主球队时，当前回退逻辑可能重复分配并覆盖归属。这是球队容量问题，与 Cloudflare Access 的席位限制无关。

**建议先选择产品方向：**

| 方向 | 实现要求 | 对玩家的说明 |
|---|---|---|
| 独立世界 + 云存档 | 保留每账号独立结算，弱化或移除全局独占球队的概念 | 每人拥有自己的经营世界 |
| 真正多人联赛 | 统一球队、赛程、比赛结果、积分榜和赛季迁移 | 玩家实际相互竞争 |

如果选择多人联赛：

1. 满服时明确拒绝接管，或分配到新的世界分区，禁止覆盖归属。
2. 球队状态与比赛结果只存在一个权威版本。
3. 双方玩家看到同一场比赛、同一比分与积分变化。
4. 明确中途加入、长期离线、弃队、赛季切换的处理规则。

**验收建议：** 同一场玩家对战从双方账号读取的结果一致；满员后注册不会改变已有球队归属。

### 3.2 转会市场存在可重复套利

**优先级：P0｜性质：已确认的经济规则问题**

代码依据：`src/game/market.ts` 中的 `buyFreeAgent()`、`settleMarket()`。

当前规则允许：

1. 按球员估值购买自由球员。
2. 按最高两倍估值挂牌。
3. 满足结算条件时由 NPC 买入。
4. 卖出的球员重新进入自由球员列表。

例如估值 50,000 的球员可买入后以 100,000 挂牌成交，再按估值买回。虽然受到轮次、转会窗口和阵容合法性等限制，仍存在可重复获利的循环。

**影响：** 倒卖可能优于正常经营，联赛收入、设施费用和转会预算失去约束力。

**建议：**

- 最小修复：NPC 收购价低于正常购入成本，消除无训练、无风险的正收益循环。
- 后续版本：加入报价、买方预算和需求，不再保证两倍估值成交。
- 卖出的球员不要立刻以更低价格回到可购买列表。
- 为买入、挂牌、成交、回购建立完整经济回归测试。

**验收建议：** 同一球员不经培养等价值变化，完成买卖回购循环后不能产生保证利润。

### 3.3 客户端快照不适合作为竞技权威数据

**优先级：P0（公开竞技前）｜性质：已确认的公平性边界**

代码依据：`server/app.ts` 的 `PUT /api/game`。

接口校验版本与部分结构，并对进行中的联赛状态做保护，但仍接受客户端上传的大部分完整存档。金币、成长、阵容等不能因此视为可信竞技数据。

**邀请码与 Turnstile 解决的是注册控制，不能解决游戏存档篡改。**

**建议：**

- 独立单机模式可继续允许客户端存档，但不要把它直接用于可信排行榜或交易。
- 多人模式改为客户端提交动作，服务器校验并计算结果。
- 优先迁移训练、确认成品、购买、挂牌、设施升级等影响竞争力的动作。
- 明确离线存档与竞技存档的边界，禁止随意导入后进入公平竞技。

**验收建议：** 不能通过上传改动后的金币或属性快照获得竞技收益；无效动作不改变服务器状态。

### 3.4 成长缺少长期差异与取舍

**优先级：P1｜性质：设计风险，需长期模拟验证**

规则依据：培养已改为按每名球员自己的属性上限截断（见下方「已落地」），但若各属性上限相对当前能力的差距趋于一致，长期训练后球员仍会向同一形状收敛；技能可通过传承获得。

**风险：**

- 长期训练后球员趋于同质化。
- 球探、招募和球员类型的重要性降低。
- 经营判断可能退化为训练次数的竞争。

不建议简单恢复“低潜力球员永远不能成才”的硬限制。可以采用：

- 高属性区间成长递减。
- 不同球员在训练效率、擅长方向和角色适配上存在区别。
- 部分特性不可完全复制。
- 专精路线有机会成本，同一球员无法轻易在全部方向同时最优。

**设计目标：** 普通球员也能成才，但成才路径与最终用途不同。

#### 明星球员差异化（已确认要做）

真实球星目前主要差异在姓名、初始属性和招牌技能。若成长路径最终收敛，明星球员会退化成"起步更快的普通球员"。

已确认原则：**明星球员要有不可通过训练复制的特征。** 具体形式待定，可选载体：

- 独占招牌技能（已部分存在，需确保不能被传承或复制）。
- 专属特性或行为倾向（如特定局面下的加成、风险偏好）。
- 训练效率的结构性差异（擅长方向广但上限增幅慢，或相反）。
- 生涯曲线差异（早熟/晚成、巅峰期长度）。

限制：不能变成"明星永远碾压普通球员"，否则青训与养成的意义消失。目标差距应是**特色不同**，而不是单纯的数值高低。

> 待确认：差异化只作用于真实球星，还是玩家培养出的球员也能获得少量稀有特性？
>
> 决策（D5c）：乙——真实球星给不可复制特征，玩家培养的球员按低概率涌现稀有特性。

#### 已落地：属性上限画像映射（第一版）

原先的实际情况是：界面显示的是球员自己的 `player.ceilings`，但培养代码把上限统一当成 1500，所以「每人上限不同」只是显示层假象。这一版修掉了这个不一致，并把上限计算抽成独立的映射层。

- `src/game/data/attr-profile.ts`：`AttrProfile`（0–1 相对权重）+ FM 1–20 评分映射 + 上限公式。
  - `FM_ATTRIBUTE_MAP` 只声明维度对应关系（如 `Finishing → shooting`、`CommandOfArea → rushing`），不搬运任何 FM 数值表。
  - `ceilingsFromProfile`：`tier` 决定「多强」，画像决定「强在哪」；招牌属性上限更高、弱点更低。
  - `normalizeCeilings`：保证「上限 ≥ 当前属性 ≤ 绝对上限」，旧存档不会被冻死。
- `src/game/data/players.ts`：生成时先由风格算权重并归一化成画像，再按画像出上限。随机源的消耗顺序与旧实现完全一致，因此其余球员数据不漂移。
- `src/game/training.ts`：培养改用 `session.candidate.ceilings`，到各属性自己的上限即停。

实测 500 名球员 × 6 项主属性（2706 个样本）：上限中位数 1161，p90 为 1416，分布 939–1485，不同取值 362 个，**没有任何一项达到 1500**；同一球员内部最高/最低上限比中位数 1.34。即：人人可练，但练到哪因人而异。

数据源现状：FM 存档（`.fm`）是 zstd 容器 + 私有序列化，解压后字符串表还是字节逆序，抽 36 项属性属于逆向工程，成本高且版本一更新就失效，因此不走这条路。改用「表格 → 导入器」两条输入：① FM 界面导出复制成 TSV；② 直接读游戏数据库导出的宽表（22 万行 × 90 列，表头形如 `技术_传球_passing`，带 CA/PA 与出生日期）。`npm run fm:import` 把 1-20 属性转成画像写入 `src/game/data/fm-profiles.generated.ts`，只覆盖上限形状，不动当前属性。当前 500 个种子里 411 名能匹配到真实数据（`fm-match.ts` 做手工别名表 + 五层名字匹配 + 位置校验 + 年代窗口），剩下 89 名（退役过早或那份导出漏掉的现役）在 `profiles-curated.ts` 里手写画像，于是 500 名球员全部有「形状」，风格画像只作为兜底。流程与映射表见 [fm-data-import.md](./fm-data-import.md)。

（`docs/AUTFabis FM24 Data Spreadsheet v2.rar` 里是一张空的公式模板，录入表只有 `Paste here`，不含任何球员数据，需要先用 FM 导出填入。）

**验证建议：** 模拟多个赛季，观察属性分布、阵容重复率、招募替换率和达到高属性区间所需的实际操作量。

### 3.5 培养操作量与 Agent 公平性

**优先级：P1｜性质：设计风险，需真人试玩验证**

一轮培养包含 30 个行动，另有事件处理和候选确认。共同训练能降低部分负担，但多球员反复培养仍可能形成大量机械操作。

如果多数行动能用固定策略完成，真人会觉得繁琐，而 Agent 能稳定高频执行，双方收益差距可能来自劳动量而不是决策质量。

**建议：**

- 支持训练计划、批量执行和常规事件自动处理。
- 关键路线、导师选择、重大事件保留明确决策点。
- 真人与 Agent 使用同样的资源预算和规则。
- 自动化应节省时间，而不是额外创造训练额度。

**验证建议：** 记录一次完整培养的耗时、点击次数和真正改变计划的决策次数；比较相同资源预算下真人与 Agent 的收益。

### 3.6 联赛开赛时间不稳定

**优先级：P1｜性质：已确认的时间规则，体验影响待验证**

代码依据：`src/game/season.ts`。

- 一个游戏日为现实 6 小时（一天 4 个游戏日）。
- 每 3 个游戏日一轮，即现实 18 小时。
- 38 轮对应约四周的赛季尺度，具体首尾时间取决于首轮开赛与结算安排。
- 单场联赛比赛约 10 分钟。

18 小时除不尽 24 小时，开赛时刻会每天往后漂 6 小时，难以形成固定的日常习惯。要求玩家经常在线临场操作，会放大真人与常在线 Agent 的差距。

> **已决策（D7=B + D7a=甲）**：轮次改为 4 游戏日 = 现实 24 小时，每天固定钟点开赛，赛季 38 天。详见 6.1。

**建议：**

- 使用每天固定时段，或明确的分区赛程。
- 支持完整的赛前战术与自动换人预案。
- 缺席不应导致球队无法执行合理计划。
- 日常经营尽量在几分钟内完成，重要比赛提供更深的手动参与。

**说明：** `FM_TICK_MS=30000` 是服务器检查推进的间隔，不是“每 30 秒完成一轮联赛”。此前部署说明中的相关表述应予纠正。

### 3.7 战术数量不等于有效策略数量

**优先级：P2｜性质：待实验验证**

当前具备阵型、职责、战术、技能与比赛统计，但比分分布正常、测试通过，并不能证明战术之间存在合理取舍。

需要进一步验证：

- 高压逼抢的收益是否对应体力、身后空间等代价？
- 控球、反击、长传是否分别适合不同阵容？
- 领先与落后时调整策略，能否改变机会结构？
- 是否存在对多数对手都占优的固定组合？
- 复盘能否让玩家理解这些差别？

**建议：** 建立战术对抗矩阵，控制阵容强度，使用多种种子与主客场交换，比较机会质量、进球、失球、体力和胜率。不能仅依据少量胜负调参。

**设计目标：** 不同战术有适用条件和反制方式，而不是存在唯一最强配置。

## 4. 已确认方向与实施路线

本节依据已确认的产品决策排序，优先级高于第 3 节中各条的独立建议。

### 4.0 已确认决策

| 编号 | 议题 | 决策 |
|---|---|---|
| D1 | 产品定位 | **C 分阶段**：先上线单机云存档，预留接口，跑通后切多人 |
| D2 | 满员处理 | **B 开新分区**：球队容量满时自动新建世界分区 |
| D3 | 转会市场 | **C 重做**：挂牉与竞价机制取代固定估值成交 |
| D4 | 竞技数据可信度 | **B 关键动作走服务器**：训练、买卖、设施升级服务端校验结算 |
| D5 | 成长曲线 | **B+C**：高属性成长递减 + 球员专精差异 |
| D7a | 轮次长度 | **甲**：24h = 4 游戏日/轮，一天一场，赛季 38 天 |
| D3a | 竞价分期 | **乙**：阶段一即做 NPC 报价系统（预算 + 成交概率） |
| D5c | 差异化范围 | **乙**：真实球星 + 玩家球员稀有特性 |
| D5b | 明星球员 | **做差异化**：真实球星拥有不可复制的特征（详见 3.4） |
| D6 | 训练自动化 | **A+B**：保留手动，同时提供训练计划与批量执行 |
| D7 | 联赛节奏 | **B 固定开赛时段**：每天在固定时间统一开赛 |
| D8 | 执行顺序 | **A → B**：先修漏洞，再改体验；模拟验证可并行 |

### 4.1 阶段一：修复与地基（D8=A）

目标：让现有原型不出错、可放心给人玩。

- 修复市场套利闭环；在竞价系统上线前，先保证不存在无风险正收益循环。
- 球队分配不再回退覆盖已有归属；满员时明确拒绝并提示。
- 纠正 `deploy/env.example` 中把服务器 tick 写成轮次长度的错误注释（已修正）。
- 明确说明当前是独立世界，不宣传为统一多人联赛。
- 建立经济与长赛季回归模拟，作为后续改动的基线。

### 4.2 阶段二：体验优化（D8=B，与 D5/D6/D7 同步）

- D5 高属性成长递减，先做最小版本并在模拟中校准。
- D5b 明星球员特征设计并落地，以"特色不同"而非"数值碾压"为约束。
- D6 训练计划与批量执行；保留事件、路线、导师等关键决策点。
- D7 固定开赛时段；因固定时段要求轮次能整除 24 小时，需把轮次长度从 3 游戏日调为 2 或 4 游戏日（见待确认事项）。
- 配套：离线预案与赛前自动换人，避免不在线就踢不了球。

### 4.3 阶段三：竞技地基（D4=B）

目标：把影响竞争力的数据变为可信数据。这是 D1 进入多人阶段的前置条件。

- 训练行动、确认成品、自由球员购买、挂牉、设施升级改为服务端校验后结算。
- 客户端不再能通过上传修改后的金币、属性或阵容获得竞技收益。
- 区分单机存档与竞技存档，并明确二者不互通。
- 为每个动作建立拒绝路径测试（非法、越权、重放、并发重复提交）。

### 4.4 阶段四：多人联赛（D1=B 目标形态）

- 统一球队、赛程、积分榜与赛季结算，比赛结果只存一个权威版本。
- D2 分区机制：满员自动开新世界，禁止重复分配。
- D3 完整竞价：在多人与 NPC 买方同时存在的市场下重做价格发现。
- 明确中途加入、长期离线、弃队与赛季切换规则。

### 4.5 阶段五：再扩充内容

完成上述验证后，再增加球员、事件、赛事与社交功能。新增内容应服务于有效决策，而不是增加重复操作或维护负担。

## 5. 建议观察的指标

| 维度 | 建议指标 | 用途 |
|---|---|---|
| 上手 | 首次完成培养、首场比赛、首次主动调整战术的比例 | 判断玩家是否理解核心循环 |
| 操作负担 | 每日操作时长、培养点击数、批量功能使用率 | 判断是否存在机械劳动 |
| 成长 | 高属性球员比例、阵容替换率、不同路线使用率 | 判断是否快速同质化 |
| 经济 | 联赛/交易收入占比、资产增长、设施升级顺序 | 识别套利与单一最优发展路线 |
| 战术 | 控制实力后的策略对抗结果、阵型使用分布 | 识别失衡配置 |
| 多人 | 比赛结果一致性、重复球队归属、异常状态变更 | 检查公平性与世界一致性 |
| 留存 | 次日/七日回访、赛季完成率、错过比赛后的回访 | 判断节奏是否适合目标玩家 |

具体目标值应在明确目标用户、进行小规模试玩后制定，不应凭当前测试通过数量推定体验已经成熟。

## 6. 已确认的补充决策

### 6.1 轮次长度：24 小时 / 4 游戏日（甲）

原为 3 游戏日一轮 = 现实 18 小时。因 18 小时无法整除 24 小时，无法在每天固定钟点开赛（开赛时间会每天往后漂 6 小时）。既然 D7=B，轮次长度已改为 24 小时：

| 项目 | 值 |
|---|---|
| 游戏日 | 现实 6 小时（一天 4 个游戏日，不变） |
| 一轮联赛 | 4 游戏日 = 现实 24 小时 |
| 赛季长度 | 38 天 |
| 一轮培养（15 游戏日） | ≈ 3.75 轮 |

影响：`ROUND_GAME_DAYS` 由 3 改为 4，同时需同步修正 `src/game/world.ts` 与 `src/game/season.ts` 中的重发常量（两处各有自己的 `ROUND_GAME_DAYS`，易漂移，应提为单一来源）。

### 6.2 竞价系统：阶段一就做 NPC 报价（乙）

不采用“先打补丁、多人再做”的分期，而是阶段一就实现 NPC 报价系统：

- 买方有预算与需求，不是任意价格都接。
- 成交有概率，两倍估值不再是保证成交。
- 卖出的球员不立即以低价回市场。

这样阶段四接入玩家出价时，只是在同一报价模型里增加一个买方类型，不需返工。

### 6.3 明星差异化：真实球星 + 玩家球员稀有特性（乙）

- 500 名真实球星拥有不可复制的特征。
- 玩家培养的球员也可低概率涌现稀有特性。
- 约束：差异体现为“特色不同”而非“数值高低”，避免明星永远碾压青训球员。

### 6.4 待确认：球星属性数据来源

真实球星目前的属性由 `src/game/data/players.ts` 中的生成器根据 `tier`（1–5 星）、`style`、位置和种子 RNG 产生，同一 tier 同一风格的人形状基本一致，这也是“明星不差异化”的根因。

**为什么不能直接抄 FM**：Football Manager 的属性是 Sports Interactive 的专有数据，直接复制存在数据库权利与著作权风险；且它是 1–20 分、36 项属性的十一人制模型，与本作 0–1500 的 18 项七人制属性不同，必须先映射。

**但参考它的思路是可行的，而且该参考的是画像（profile）而不是总评（CA）**：FM 真正的价值是“这个人是哪种球员”（抢点型、组织核心、抢断型后腰），而不是 89 这个数字。

可行方案：

1. 每个球星补一组 6 维画像（进攻/组织/防守/身体/技术/精神），写入 seed。
2. 属性生成改为：**tier 决定多强，画像决定强在哪**。
3. 仓库内 `docs/star-pool-extra-cn.csv` 已含 FIFA23 的 `overall`，可作为第一版数据来源。
4. 数据缺失时回退到现有生成器，保证 500 人不依赖外部数据才能运行。

> 待选：只用户仓库内现成的 FIFA23 数据做第一版，还是再引入外部公开统计（如 FBref per-90）把画像做细？

> 待选：甲简单可控，乙更耐玩但会影响所有成长数值的校准。

## 7. 最终建议

**优先增加决策价值，而不是系统数量。**

当前已有能玩的骨架。下一步最有价值的工作是修复经济循环、明确多人边界、保证竞技数据可信，并让玩家把时间花在选择与复盘上，而不是重复点击。
